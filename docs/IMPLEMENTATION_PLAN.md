# QuantView2027 实施与验收计划

> 更新：2026-10-27｜状态：逐项记录实现与验收，阶段整体尚未完成
> 依据：[开发设计](DEVELOPMENT_DESIGN.md)、[看板、邮件与复盘设计](WORKBENCH_DESIGN.md)

## 1. 交付原则

复用行情、指标、AI 和 Streamlit 基础，先建立可信版本，再改善展示、记录与提醒。当前只完成静态代码核对，实际行情连续运行、邮件和用户使用效果需要分别验收。

10 月 24 日已提交完整性基础，10 月 26 日实现日历与目标日选择，分别见 [10 月 24 日进度](PROGRESS_2026-10-24.md) 和 [10 月 26 日进度](PROGRESS_2026-10-26.md)。本表不将单项进展当作阶段完成；每项登记代码 / 测试或运行证据。

优先级表示依赖顺序，不是并行授权或固定工期。若上游数据无法确认完整，先交付明确的部分 / 失败状态，不以 UI 完成代替数据验收。

关键修复点：

- `_run_ai()` 已传入实际合约完整性并阻断不完整品种；继续补齐历史窗口、替代价等质量依赖，保留现有门禁回归测试。
- `render_daily_report()` 已按本轮完成品种过滤历史 AI；继续将同日“最新 AI”查询改为显式分析版本与快照引用。
- `AIWorkflow.run()` 不再按仅含数据输入的 ID 覆盖模型 / 提示词变更。
- `DailyPipeline.run()` 获锁后创建运行记录，避免锁外写库。
- 当前主力候选的到期过滤、固定价差配置、预热窗口说明补齐；配置未应用不能在 UI 显示为已生效。
- 历史回填补齐历史真实合约清单；无法补齐时保留覆盖限制。
- 当前 `status` 命令和看板可以渐进兼容，但必须明确 run success 与 data complete 的区别。

P0 退出条件：新增数据契约与迁移可复现；现有离线测试通过；完整、部分、无数据、无 AI、修订五类小型 fixtures 均可发布 / 查询且不混用版本。真实数据质量未确认时不启用无人值守邮件。

## 6. P4：试运行与使用评估

**交付结果：确认系统可靠运行与实际使用价值，再决定后续投入。**

工程验收：连续 5 个经核验交易日，按期运行或明确记录未运行原因；每日目标数据状态可解释，异常 / 恢复消息符合策略，无重复日报；所有报告能回到相同证据和版本。失败后重跑可以恢复，但原失败记录不能删除。

使用观察：再经过若干周真实使用，记录是否持续查看摘要、是否愿意填写理由、是否按期复盘、邮件信息量是否适中、手机访问是否成为实际障碍。观察时长不是策略有效性检验。

| 观察结果 | 后续选择 |
|---|---|
| 邮件已足够，偶尔在电脑深入研究 | 维持本地看板与邮件 |
| 经常外出需要查历史 / 记记录 | 先独立设计受保护的手机网页访问 |
| 手机网页仍存在明确阻碍 | 再评估微信小程序，复用现有快照 / 服务 |
| 主要问题是证据缺少供需信息 | 优先论证新增数据源，而非更换展示端 |
| 记录显示违反规则较多 | 检查规则是否清楚、流程是否可执行；不直接认定应加自动下单 |
| 按规则执行仍表现差 | 另立策略验证 / 绩效归因任务，不能只优化界面或 AI 提示词 |

| AT-06 | 同日重跑且内容相同；修正数据产生不同内容 | 相同内容复用并留运行关联；新内容另存，不改变旧记录引用 |
| AT-07 | 发布过程中宕机、文件丢失或哈希不符 | 半成品不可见，恢复 / 隔离有记录，禁止据此投递 |
| AT-08 | 同时补跑、保存笔记、领取邮件 | 单写锁与短事务生效；表单不丢失；无重复逻辑投递 |
| AT-09 | SMTP 明确拒绝、正文后超时、进程 sending 时崩溃 | 分别 failed / unknown / unknown；有界重试，未知需核对 |
| AT-10 | 纪律更换、记录更正、后补过去决策、使用未来快照 | 原版本保留；后补可见；未来证据不得判定为事前合规 |
| AT-11 | 周边界、无适用规则、全为未知或无到期记录 | 周区间正确，统计带分母，零样本无百分比幻觉 |
| AT-12 | 全新空库、失败运行、历史回填、恢复备份 | 状态 / 记录入口可访问，历史不自动发送，恢复引用与哈希可校验 |
| AT-13 | 非连续 5 次成功，或旧回填失败恰为最后一条运行 | 不通过连续试运行；当前目标日健康与历史错误分开显示 |
| AT-14 | 390px 窄屏、无远程地址、HTML 含用户特殊字符 | 页面不遮挡主信息；邮件无无效跳转；正文正确转义 |

不为纯文档变更增加运行测试。后续代码实现按对应阶段运行现有相关测试与上述业务场景，避免反复执行不相关网络测试或向真实邮箱发送测试风暴。

## 8. 开发完成定义

每个任务需同时满足：行为与设计一致；相关失败场景验证通过；默认配置安全且未悄悄启用投递 / 调度；文档标记与实际命令一致；迁移与恢复说明可执行；无真实凭据 / 个人记录进入版本控制。

需更新的实现入口：`README.md`、`config/app.yaml` / 配置校验、`.env.example`、`.gitignore`、CLI 帮助、表结构迁移和对应测试。示例配置应注明适用版本，不能提前宣称计划命令已经可用。

完成状态应附代码路径、测试结果和必要的脱敏截图 / 运行记录。仅有 5 个交易日稳定运行不代表投资纪律或趋势策略已经取得统计验证。

10 月 27 日看板查询版交付、测试与限制见 [进度记录](PROGRESS_2026-10-27.md)；不据此将 P0 / P1 整体标记完成。

## 1. 文档目的

本文档定义 QuantView2027 的产品边界、数据架构和计算口径。下一版以“看板为主、邮件为辅、决策与复盘留痕”为方向，帮助个人形成可追溯的研究过程，不以界面升级或 AI 分析替代策略验证。

去年投资表现不佳的原因尚未通过交易记录核验；本项目不能预设原因是信息不足、执行失误或策略失效，也不承诺通过增加功能改善收益。

### 1.2 使用目标

- 收盘后用几分钟确认数据质量与重要变化，需要时再深入研究。
- 每条研究结论能回到当时的数据、证据、规则和 AI 版本。
- 能记录“观察、暂不行动、手工决策”及其理由，按期复盘。
- 分开衡量数据可靠性、记录习惯与纪律执行；缺乏真实成交与资金数据时，不展示投资收益率、夏普或策略胜率。

第一版不追求构建完整量化交易系统，而是先打通一条稳定、可验证、可追溯的日频投研链路：

> 日行情采集 → 数据校验与确定性指标 → 证据与可选 AI 分析 → 不可变研究快照 → 看板 / 日报 / 邮件摘要 → 手工决策记录 → 独立复盘

## 2. 核心决策

### 2.1 部署和运行形态

采用 **Local-first Python 应用**：

- Python 负责数据采集、计算、AI 调用、报告生成和本地 Web UI。
- DuckDB 保存标准化数据，Parquet 保存原始数据快照。
- Streamlit 提供本地可视化工作台。
- Windows 任务计划程序在交易日收盘后运行一次日任务。
- 目标：工作台启动时展示缺失交易日，用户明确触发补跑；当前只有“检查并补跑今天”按钮。
- GitHub 仅用于源代码版本管理、测试和备份，不作为第一版运行后台。
- 本地模式无需 24 小时常驻；每日任务及邮件投递结束后可退出，浏览看板时启动应用。电脑关闭期间无法采集、发邮件或监测失败。

默认日终任务时间为 `Asia/Shanghai` 18:10，这是数据采集时间，不代表上游此时一定更新完毕，也不提供盘中风控。交易日标识与日历、补跑策略见第 11 章；Windows 任务目前按周一至周五触发，其他操作系统仅支持手动命令，自动调度需另行实现。

### 2.1.1 展示渠道决策

| 渠道 | 定位 | 下一版安排 |
|---|---|---|
| 本地看板 | 深入研究、证据追溯、规则检查、决策与复盘 | 主入口，复用 Streamlit |
| 邮件 | 日终短摘要、运行异常和每周复盘提醒 | 从同一研究快照生成，默认关闭，配置后启用 |
| 手机网页 | 有明确外出查询需求后的延伸 | 后续评估受保护的远程访问；本地链接不当作手机可访问地址 |
| 微信小程序 | 独立移动入口 | 暂缓，不新建第二套计算与分析链路 |

看板的市场数据区域保持只读；仅允许通过受控表单保存个人研究记录、纪律版本及复盘，不增加账户连接或订单操作。

### 2.2 技术选型

| 层次 | 第一版选型 | 说明 |
|---|---|---|
| 语言 | Python 3.11/3.12 | 满足 AKShare 当前版本要求 |
| 包与环境管理 | `venv` / pip + `pyproject.toml` | 当前安装方式；锁文件与 `uv` 工作流尚未落地 |
| 数据处理 | Pandas | 三个品种的日频数据规模较小 |
| 标准数据仓库 | DuckDB | 单文件、适合时序与横截面分析，无需数据库服务 |
| 原始数据 | Parquet | 保存上游原始快照，支持追溯和重算 |
| 数据源 | AKShare adapter | 首期免费数据源，必须隔离在适配层之后 |
| 配置 | YAML + `.env` | 业务参数与密钥分离 |
| AI 接入 | 轻量 provider adapter | 支持 OpenAI-compatible API，首期不引入完整 LangGraph |
| 报告 | Jinja2 → Markdown；计划增加邮件 HTML / 纯文本 | 全部绑定同一不可变研究快照 |
| UI | Streamlit + Plotly | 快速完成个人本地工作台 |
| 测试 | Pytest | 覆盖数据口径、换月、价差和异常处理 |
| 调度 | Windows Task Scheduler | 当前仅有 Windows 脚本；跨平台调度后续实现 |
| 邮件（计划） | 标准库 SMTP + outbox | 默认关闭，凭据从环境读取，单独记录投递状态 |

## 3. 产品范围

### 3.1 MVP 纳入范围

1. LH、JD、C 全部有效挂牌合约的日行情。
2. OHLC、结算价、成交量和持仓量。
3. 主力、次主力识别及主力切换记录。
4. 同品种合约期限结构和跨期价差。
5. 成交量、持仓量的日变化、占比和滚动异常度。
6. 价格—成交—持仓的确定性状态描述。
7. Bull、Bear、Judge 三角色 AI 分析。
8. Markdown 日报、历史日报和本地可视化工作台。
9. 数据来源、数据新鲜度、质量标记和运行状态展示。

### 3.2 下一版纳入范围

1. 品种独立卡片与小图、重要变化摘要、换月及数据质量提示。
2. 显式交易日历、目标日期完整性门禁、快照和日报版本管理。
3. 从共享快照生成日终邮件，支持预览、去重、失败与恢复通知。
4. 个人纪律的版本化保存；仅对用户明确配置且可确定计算的条件做检查。
5. 手工研究决策、暂不行动记录、追加修订、独立复盘及周度汇总。
6. 本地个人记录导出、备份与可验证恢复。

下一版不预置已被证明有效的投资策略，不从节目描述推导“温度”算法或具体开平仓阈值。

### 3.3 本轮排除范围

- 实盘 / 模拟盘下单、账户连接、自动仓位及止损执行。
- 分钟行情、盘中告警、保证金监控或交易风险监控。
- 策略回测、真实组合收益归因、自动成交匹配。
- 新增期权、库存、仓单、基差、养殖利润、天气、新闻及会员排名数据。
- 多用户服务、公网发布、微信小程序与移动端重写。

研究记录中的“观察条件”不构成交易指令；手工记录用户在外部做过的决定也不代表系统执行过交易。

## 4. 架构总览

```text
AKShare / 手工文件
        ↓
Adapter → 原始 Parquet → 标准化与校验 → DuckDB 当前计算视图
                                              ↓
                         指标 + 质量门禁 + Evidence Pack
                                              ↓
                                 可选 Bull / Bear / Judge
                                              ↓
                      不可变 ResearchSnapshot + 日报版本
                          ├─ Summary Builder → 本地看板
                          ├─ Markdown / HTML / 纯文本
                          ├─ outbox → 邮件投递记录
                          └─ 规则检查结果 → 手工决策 → 独立复盘 → 周报
                                            ↑
                                    已激活的纪律版本
```

研究快照、共享摘要、邮件及日志为目标新增模块；现有行情标准表继续用于最新查询与重算，不能充当“当时所见”的唯一依据。

### 4.1 分层原则

1. **数据源隔离**：除 adapter 外，任何模块不得直接 import 或调用 AKShare。
2. **原始数据不可变**：成功抓取的原始响应以批次保存，不覆盖历史快照。
3. **先计算、后解释**：收益率、价差、Z-score 等由确定性代码计算，LLM 不负责算数。
4. **AI 可降级**：AI 失败不能阻止行情与确定性日报生成。
5. **可重跑**：相同交易日重复运行必须幂等；修复数据后可按日期重算。
6. **可追溯**：每份报告均能定位数据源、抓取批次、代码版本、提示词版本和模型。
7. **研究边界**：不创建 `broker`、`order`、`execution` 等交易执行模块；个人记录只能通过受控服务写入。
8. **版本一致**：同一快照驱动看板、日报与邮件，禁止各渠道独立调用 AI 得出新结论。
9. **时间可追溯**：标准行情可以修正；已发布快照、已提交个人记录和已激活纪律版本只追加，不原地覆盖。
10. **投递解耦**：邮件失败不回滚行情与报告；回填历史默认不发送历史邮件。
11. **配置可追溯**：快照保存数据、规则、代码、提示词及摘要配置版本；密钥不进入快照。

## 6. 数据源设计

### 6.1 数据源优先级

| 优先级 | 数据源 | 用途 | 降级策略 |
|---|---|---|---|
| P0 | AKShare `futures_zh_daily_sina` | 单个真实合约历史日线 | 失败后转 P1 |
| P1 | AKShare `futures_hist_em` | 单合约日线回退 | 字段标准化后校验 |
| P2 | 手工文件导入（CSV 为基础） | 免费接口全部失效时兜底 | 明确标记 `manual`；Excel 读取还需相应引擎依赖 |
| 辅助 | `futures_zh_realtime` | 当前合约发现 | 当前实现使用本地活跃注册表；无记录时推导候选代码 |

交易所级 `get_futures_daily(..., market="DCE")` 不作为首期关键依赖。其 DCE 接口存在长期不可用记录，只有在数据可行性验证通过后才能作为额外来源。

### 6.2 Adapter 与标准化契约

当前 adapter 返回 `FetchResult`（来源、代码、抓取时间、批次、DataFrame 与元数据），随后 normalization 生成标准 `DailyBar`；下列为跨层目标字段集合，不是当前已存在的 `DailyBarRaw` 类：

```text
Canonical daily bar fields
  source
  source_symbol
  exchange
  product
  contract_code
  trade_date
  open
  high
  low
  close
  settlement
  pre_settlement?
  volume
  open_interest
  turnover?
  fetched_at
  raw_batch_id
```

Adapter 只负责获取和最低限度解析；类型转换、合约标准化、业务校验在 normalization/validation 层完成。

### 6.3 合约发现

当前实现的候选优先级如下（不是三者并集）：

1. 当前接口成功发现的 LH/JD/C 合约，成功时以此集合为准；
2. 发现失败时使用本地 `instrument` 活跃记录；
3. 发现失败且无本地记录时，根据交割月份推导未来候选合约代码。

系统不得只抓主力连续合约，否则无法可靠计算期限结构、价差及持仓迁移。历史回填必须另外补齐目标时期的已到期合约清单；当前合约发现不能证明历史横截面完整。

### 6.4 原始快照

建议路径：

```text
data/raw/{source}/{trade_date}/{run_id}/{endpoint}_{symbol}.parquet
```

同时保存：请求参数、AKShare 版本、抓取时间、响应行数和内容哈希。原始快照用于复核供应商字段变化和离线重算。

## 8. 核心计算规则

### 8.1 主力与次主力

目标规则（当前代码已有排序及换月记录，到期过滤与缺失回退需按实施计划补齐）：

1. 过滤非真实合约、已到期合约和无效数据。
2. 以当日 `open_interest` 降序选主力和次主力。
3. 持仓缺失时才允许以成交量回退，并设置质量警告。
4. 主力相同持仓时，优先成交量更高的合约；仍相同时选择近月。
5. 保存每日选取结果，不使用今天的结果回写历史。
6. 主力切换日同时展示旧主力和新主力，避免把换月跳空解释为单合约收益。

连续趋势展示与真实合约分析分离。供应商连续合约不得用于跨期价差。

### 8.2 合约价差

首期只支持同品种跨期价差：

```text
settlement_spread = near.settlement - far.settlement
close_spread      = near.close - far.close
spread_pct        = settlement_spread / near.settlement
```

默认以结算字段价差作为研究主口径；东方财富降级时该字段可能来自收盘价，必须展示 `settlement_filled_from_close`，不可称为交易所结算价。合约对包括：

- 主力与次主力构成的合约对（按交割月份排序，数值始终近月减远月）；
- 按交割月份相邻且满足流动性条件的合约；
- 配置文件指定的固定观察合约对（目标能力，当前引擎未应用固定对配置）。

不默认计算年化展期收益率。若后续加入，必须根据真实交割月份间隔计算，并明确年化假设。

### 8.3 流动性过滤

阈值放入配置，不能硬编码。当前引擎已标记价差两腿的成交 / 持仓阈值，完整过滤仍待完善。目标支持：

- 最低当日成交量；
- 最低持仓量；
- 是否允许零成交但仍有持仓的合约；
- 距最后交易日的最小天数；
- 近远月两腿是否均满足条件。

最终阈值在数据可行性阶段根据 LH、JD、C 的实际分布确定。

### 8.4 成交与持仓变化

同时计算单合约和品种汇总口径：

```text
volume_change     = volume[t] - volume[t-1]
oi_change         = open_interest[t] - open_interest[t-1]
main_volume_share = main_volume / product_total_volume
main_oi_share     = main_oi / product_total_open_interest
```

主力切换时，主力序列的变化不得直接使用新旧两个合约相减。单合约变化按合约自身历史计算；品种变化按全部有效合约汇总后计算。若合约覆盖集合发生变化，必须提示汇总变化含样本变化因素。

### 8.4.1 收益与换月展示口径

当前 `return_5d/20d` 是每日所选主力的“自身合约日结算变化率”连乘，既不是某一真实合约持有至今的收益，也不是含换月成本的可交易策略收益。界面统一标注“主力日变化链式指标”。未补齐目标窗口交易日、样本或替代价说明时，显示缺口，不将跨缺失日变化误标为一日收益。

单合约详情使用同一合约序列。主力价格历史按合约分段、换月处断线并标记旧 / 新合约；不把新旧合约价格差当成收益。三品种价格使用独立纵轴小图，不画成同一价格纵轴，也不将当前链式指标改名为净值。

当前 ATR20 最少 5 条样本即计算；Z20 / Z60 及分位数最少分别 5 / 15 条即计算。下一版须附样本数与预热状态；窗口未满时不得展示为完整 20 / 60 个交易日统计。

### 8.5 量价仓状态

第一版只给出观察性分类：

| 价格变化 | 持仓变化 | 状态代码 | 表述 |
|---|---|---|---|
| 正 | 正 | `up_add` | 上涨伴随增仓 |
| 正 | 负 | `up_reduce` | 上涨伴随减仓 |
| 负 | 正 | `down_add` | 下跌伴随增仓 |
| 负 | 负 | `down_reduce` | 下跌伴随减仓 |
| 接近零 | 任意 | `flat` | 价格变化不显著 |

总持仓不能识别多头和空头分别是谁，系统及 AI 均不得仅凭该四象限断言“多头主动增仓”或“空头主动增仓”。

## 9. 数据质量规则

### 9.1 阻断性错误 `rejected`

- 合约代码无法解析。
- 交易日无效。
- OHLC 明显违反 `low <= open/close <= high`。
- 价格、成交量或持仓量为非法负数。
- 同一来源同一主键出现内容冲突且无法确定正确记录。

### 9.2 警告性错误 `warning`

- 结算价缺失但收盘价存在。
- 成交量为零但仍有持仓。
- 单日价格、成交量或持仓变化超出配置阈值。
- 主源与备源在同字段上的差异超过容忍度。
- 活跃合约数量明显少于近期水平。
- 目标交易日数据尚未全部更新。

### 9.3 数据完整性门槛

当前 `pipeline_run.status` 使用 `running/success/partial/failed`，已增加目标日相对于本次已知合约集合的完整性检查；AI 使用实际完整性摘要，未确认的本地候选集合降为部分。完整性检查尚未核验交易所全挂牌、窗口与所有质量依赖。目标需分开保存：

- 任务状态 `run_status`：沿用上述任务枚举。
- 数据状态 `data_status`：`complete/partial/failed`，由目标日逐品种质量门禁计算。
- AI 状态 `ai_status`：`success/partial/skipped/failed`，与数据质量无关。
- 邮件状态：独立 outbox 枚举，见配套设计。

当前逐品种门禁使用 `complete/partial/missing`；目标在发布层将 `missing` 归入无可用数据并汇总为以下三种数据状态，保留逐品种原因：

- `complete`：三品种满足最低完整性并完成全部指标。
- `partial`：确定性数据部分缺失，但报告明确标记缺口。
- `failed`：关键日行情不可用，不生成市场结论，仅生成失败报告。

目标：AI 分析只在对应品种 Evidence Pack 达到质量门槛时运行。门槛至少核验目标日期匹配、预期合约覆盖、主力选择所需字段、历史窗口及质量标记；主力只有一条有效行情不能证明整个品种完整。结算替代可以保留观察，但须标记并按规则限制依赖真实结算的条件。日终失败时只发布异常快照，不生成当日市场结论。

## 10. AI 分析设计

### 10.1 工作流

```text
Evidence Pack
    ├─ Bull Analyst：构造最强看多论证
    ├─ Bear Analyst：构造最强看空论证及反例
    └─ Judge：比较证据强弱，给出条件化结论
```

当前 Bull 与 Bear 顺序执行，Judge 读取两者结果。并行属于可选优化，不是下一版验收前提。不使用递归辩论，也不赋予 AI 自主调用外部工具的能力。

### 10.2 Evidence Pack

每个品种的输入至少包含：

- 数据日期、来源与完整性；
- 主力、次主力及是否换月；
- 主力价格变化、5/20 日收益、ATR；
- 品种成交与持仓变化；
- 主力成交和持仓占比；
- 关键价差、历史 Z-score 和分位数；
- 异常指标和质量警告；
- 可引用的 evidence ID。

不在 Evidence Pack 中的信息，模型不得作为事实写入结论。

### 10.3 结构化输出

模型输出必须通过 schema 校验，至少包含：

```json
{
  "bias": "bullish | neutral | bearish | insufficient_data",
  "confidence": 0.0,
  "thesis": "...",
  "evidence_ids": ["..."],
  "counterarguments": ["..."],
  "risk_flags": ["..."],
  "invalidation_conditions": ["..."]
}
```

`confidence` 只是模型对证据一致性的自评，不得描述为统计显著性或胜率。

### 10.4 防幻觉与降级

- 提示词明确禁止补充未提供的供需、政策、天气、现货和新闻事实。
- 当前已有 Evidence ID 和部分字段校验；目标还需严格类型校验、非空论证和数值引用核对。重试与 JSON 修复尚待落实，最多一次，仍失败则降级。
- 单个品种 AI 失败不影响其他品种和确定性报告。
- 未配置 API Key 时，系统生成无 AI 章节的完整数据日报。
- 报告不得出现具体手数、开仓/平仓指令或自动执行建议。
- 当前 `analysis_id` 只由日期、品种和输入哈希前缀组成；目标新增独立版本 ID，包含完整输入哈希、模型、提示词内容哈希和代码 / 配置版本，保留所有修订。
- 报告只能引用本次快照明确绑定的分析；当前已有按本轮 AI 完成品种过滤的基础保护，还需替换为显式 `analysis_version_id`，彻底隔离历史与本轮输出。
- 界面将 AI 放在指标与证据之后；`confidence` 只在展开详情展示“模型自评”，不用进度条或“成功概率”。

## 11. 日任务设计

### 11.1 时间与日历

- 统一以 `Asia/Shanghai` 判断日期和截止时间；当前代码多用主机本地日期，需迁移。
- `trade_date` 使用供应商交易日标签，不将自然日晚间时间自行映射成交易日；本系统只处理已结束交易日的日频数据。
- 目标交易日由已核验的 DCE 日历确定。日历需记录来源、覆盖范围、导入时间；范围外不得默默按工作日判定完整。
- 日历不可用时可查看已有数据，但暂停自动补跑与自动日终邮件，提示人工核验目标日期。手动运行要保留覆盖警告。
- 18:10 之后可做有限次数的数据就绪重试；次数、间隔和截止时间可配置。不能因时间已到就把不完整数据标为成功。

### 11.2 目标正常时序

```text
定时 / 手动触发 → 日历与目标日检查 → 获取全局写锁 → 创建运行记录
 → 发现合约 → 抓取、原始快照、标准化、校验、幂等入库
 → 指标计算 → 逐品种质量门禁 → 证据包落盘
 → 可选 AI → 绑定本轮分析 → 生成不可变研究快照及日报版本
 → 更新运行记录 → 释放写锁
 → 根据发送策略创建 / 领取 outbox → 投递摘要 → 单独保存邮件状态 → 退出
```

失败任务也应产生带元数据的异常快照；写库失败时至少写本地错误日志。机器未开机或任务未启动时，本地程序无法自发通知，须在下次启动时提示漏跑。

### 11.3 启动和历史补跑

启动只做轻量检查，不自动发起网络请求、AI 或邮件。显示最新完整日、最新部分日和缺失区间。用户选择补最近一个缺失交易日或指定区间；防重复点击，展示运行状态。

历史回填默认关闭 AI 与邮件，仅重建数据与指标；可单独选择生成研究快照。需要注明“事后生成”，不得伪装成当时已发布的观点，也不能用于事前决策的纪律检查。

### 11.4 幂等与并发

- 所有修改 DuckDB 的入口（采集、迁移、导入、个人记录、邮件状态）共用同一个短时写锁协议；现有 `pipeline_lock` 只保护部分任务，不能视为完整并发保证。
- 运行记录也须在拿到写锁后创建。网络投递不能长时间持有数据库写锁，outbox 领取 / 完成各用短事务。
- 用户记录提交遇到采集占锁时明确提示稍后重试，保留表单内容；不得静默丢弃或在多个进程同时写同一数据库。
- 读取遇到占用时展示上次已提交快照与状态，避免让页面持续持有 DuckDB 连接。
- 事务提交标准数据后才发布快照；快照索引与文件采用准备 / 发布流程，启动可核对不完整发布并恢复。
- 标准行情按主键修正，原始 Parquet 和发布快照追加保存。相同内容重跑可复用快照，不重复投递；不同内容生成新版并标明修订。
- 锁异常退出后核查进程身份及运行记录，再允许人工解除；不按文件年龄直接删除活跃锁。

## 12. Markdown 日报设计

当前兼容路径（重跑会覆盖，尚不满足历史审计）：

```text
reports/daily/{YYYY}/{MM}/{YYYY-MM-DD}.md
```

目标版本归档、稳定快照引用及“当时版本 / 最新修订”切换见《看板、邮件与复盘设计》第 3 章。兼容路径只作为最新版本副本；个人记录必须引用不可变 `snapshot_id`，不能引用这个可变路径。

固定结构：

1. 报告元数据：交易日、生成时间、代码版本、数据来源、完整性。
2. 市场总览：LH/JD/C 主力、涨跌、成交持仓变化、关键价差和 AI 偏向。
3. LH 分析。
4. JD 分析。
5. C 分析。
6. 期限结构和跨期价差。
7. 成交量、持仓量和主力迁移。
8. Bull/Bear/Judge 观点及推翻条件。
9. 数据质量与缺失项。
10. 风险声明：仅用于个人研究，不构成投资建议，无下单功能。

日报必须保留模型和数据的不确定性，不得用单一“看多/看空”标签替代证据和反例。

| 期限结构 | 两腿是否可比？价差怎么变化？ | 历史日对照、固定合约对、两腿流动性、样本数、替代价提示 |
| 日报与系统状态 | 看的是哪个版本？运行是否完成？ | 版本选择、日报、缺失范围、采集 / AI / 邮件分开显示 |
| 纪律与记录 | 当时依据哪套规则做决定？ | 纪律版本、确定性检查、手工决定、修订历史 |
| 复盘 | 当时依据是否成立？有没有遵守规则？ | 到期列表、反证核对、执行与结果分开评价、周度汇总 |

市场数据保持只读；补跑与个人记录保存经受控服务写入，不允许页面任意 SQL 或改写行情。首页显示数据日期而非默认今天；无数据时仍能进入系统状态、个人记录和备份入口，不能由全局 `st.stop()` 阻断所有页面。

## 14. 配置设计

以下为目标配置职责，并非所有现有字段都已被代码使用。正式新增字段时必须同步类型、默认值、验证与帮助说明。

`app.yaml`：

- 数据目录和报告目录；
- 交易日任务时间；
- 默认回看窗口；
- 数据源顺序与重试；
- 当前 `data_quality.min_contracts_per_product` 默认 2，仅是最低数量，不等于挂牌集合完整；
- AI 是否启用、模型名、超时和最大预算；
- 日志级别；
- 新增时区、日历、首页摘要、快照、邮件与个人记录配置，详见配套设计第 9 章。

`products.yaml`：

- LH/JD/C 名称、交易所、允许交割月份；
- 合约乘数、最小变动价位；
- 流动性阈值；
- 价格异常阈值。

`spreads.yaml`：

- 默认主力－次主力；
- 是否生成全部相邻月价差；
- 固定观察合约对；
- Z-score 窗口；
- 到期过滤规则。

`.env` 只保存密钥和服务地址，不得提交 Git。

## 15. 日志、审计与安全

- 使用结构化日志，包含 `run_id`、`trade_date`、`stage`、`source`。
- 日志不得输出 API Key、完整请求头或含密钥的 URL。
- 每次 AI 调用记录 provider、model、耗时、token 用量和输入哈希。
- 保存提示词内容版本与证据输入；个人笔记默认不发送给 AI，不将邮件收件人和 SMTP 凭据放入 AI 输入。
- Git 忽略 `.env`、DuckDB、原始行情、生成报告和运行日志；新增快照、个人记录与备份路径落地时同步扩充忽略规则。
- Streamlit 默认只监听 `127.0.0.1`，不直接暴露到公网。
- 项目中禁止引入交易账户凭证和订单执行依赖。

## 16. 测试与验收

保留现有合约解析、价差、换月、数据校验、AI 引用、手工导入及状态测试，新增测试以可观察的业务失效场景为中心，不以“函数被调用”代替验证。

重点检查：交易日与时区、目标日真实完整性、降级价标记、AI 旧版本隔离、不可变快照、邮件投递不确定状态、记录追加修订及迁移恢复。具体场景和逐阶段通过标准见 [实施与验收计划](IMPLEMENTATION_PLAN.md)。网络测试需显式标记并默认跳过；邮件测试用假投递器，不能向真实收件人自动发送。

连续 5 个交易日可靠运行是工程稳定性验收，不证明策略有效；连续日期必须按已核验交易日历计算，不能累计任意 5 次成功。个人记录覆盖与规则检查指标须显示分母和未知数量，不能当成投资绩效。

## 17. 实施顺序

1. P0：修正日历、质量门禁、版本一致性、写锁及迁移基础。
2. P1：共享摘要与看板重构，解决价格尺度和换月展示。
3. P2：纪律版本、手工记录、独立复盘及备份恢复。
4. P3：启用日终邮件、异常 / 恢复通知和每周复盘摘要。
5. P4：连续试运行并评估移动查询需求；未出现明确需求前不开发微信小程序。

按依赖顺序交付，不给未核验的数据源可用性安排固定工期。每个阶段需有可独立验收的结果；任务、依赖与验收编号见配套实施计划。

## 18. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| DCE 免费接口变更或失效 | 当日行情缺失 | Adapter 隔离、双源回退、原始缓存、CSV 兜底 |
| 供应商连续合约口径不透明 | 趋势收益失真 | 核心分析使用真实合约，自行记录主力切换 |
| 合约代码跨年解析错误 | 合约排序与价差错误 | 明确标准标识，使用回归 fixtures 测试 |
| 主力切换造成伪涨跌 | 日报结论错误 | 单合约收益与连续展示分离，换月日显式提示 |
| LLM 编造基本面或多空行为 | 形成虚假确定性 | 仅允许引用 Evidence Pack，schema 和 evidence 校验 |
| 电脑在计划时间关闭 | 当日报告未生成 | 启动补跑；后续再考虑 NAS/VPS/GitHub Actions |
| 历史日报或 AI 被覆盖 / 混入 | 无法复现当时判断 | 不可变快照、显式分析引用、事后版本标记 |
| 邮件重发或投递状态不确定 | 通知骚扰或误以为已送达 | outbox 去重、独立状态、unknown 人工核对 |
| 个人笔记与行情并发写入 | 冲突或记录丢失 | 统一写锁、短事务、可恢复表单与备份 |
| Streamlit 后期扩展受限 | 复杂交互困难 | 保持业务服务与 UI 解耦，有实际需要再迁移前端 |

## 19. 后续路线

本轮完成后再按实际需求选择：受保护的手机网页访问；现货 / 基差 / 养殖利润等新证据；历史策略回测与真实绩效归因。它们各自需要独立数据定义和验收，不与界面改造捆绑。

微信小程序只有在持续使用记录证明手机网页无法满足查询 / 记笔记需求时再评估。任何新渠道复用研究快照与摘要，不另起一套策略或 AI 结论。

实盘下单始终不属于本项目默认路线；改变边界需独立立项。
